# SecureLayer Communication Protocol

SecureLayer uses Protocol Buffers for security-plane messages and gRPC for internal SDK, service-to-service, and server-to-server communication. Public administrative APIs remain REST endpoints in `security-core`.

## Transport

- Internal security communication uses gRPC over TLS 1.3.
- Device-bound SDK calls should use mTLS when device identity is required.
- Public administrative operations use REST with OAuth/OIDC bearer tokens and RBAC.
- Protobuf contracts live in `proto/securelayer/v1`.

## Required Metadata

Every non-health gRPC call must include:

- `x-request-id`: globally unique request identifier.
- `x-request-timestamp`: ISO-8601 instant, for example `2026-10-10T09:00:00Z`.

The server checks these values with the cryptographic replay protector. Reused request IDs and timestamps outside the accepted clock skew are rejected.

Calls may also include:

- `x-message-sha256`: base64-encoded SHA-256 hash of the serialized protobuf request.

When `x-message-sha256` is present, SecureLayer validates it before dispatching the request handler.

## Protocol Envelope

Messages that need in-band protocol metadata use `ProtocolEnvelope`:

- `request_id`
- `timestamp`
- `direction`: `CLIENT_TO_SERVER`, `SERVER_TO_CLIENT`, or `SERVER_TO_SERVER`
- `tenant`
- `protocol_version`

Metadata headers are still required for server-side replay checks because interceptors can reject invalid requests before service code runs.

## Domain Messages

`common.proto` defines shared messages for:

- `Identity`
- `Device`
- `Application`
- `Policy`
- `Authentication`
- `Encryption`
- `Integrity`
- `Signature`
- `Certificate`
- `AuditEvent`
- `SecurityDecision`
- `RequestContext`

The protocol uses structured enums for roles, device state, certificate status, and policy decisions.

## Policy Decisions

The policy decision model supports:

- `ALLOW`
- `DENY`
- `REQUIRE_MFA`
- `REQUIRE_DEVICE_CERTIFICATE`

Default behavior is deny. Clients must treat unknown or missing decision values as deny.

## Cryptographic Metadata

The protocol does not define custom cryptographic algorithms. It names the algorithm and carries metadata for operations handled by dedicated security services:

- `Encryption`: algorithm, key id, key version, nonce, associated data.
- `Integrity`: SHA-256 hash and optional HMAC metadata.
- `Signature`: Ed25519 signature metadata.
- `Certificate`: X.509 certificate status and validity window.

## Services

`DataPlaneService`

- `Authorize`: evaluates security decisions for requests.

`ControlPlaneService`

- `GetPolicy`: retrieves the active policy document and SHA-256 hash.
- `ValidateCertificate`: validates a device certificate for internal control-plane flows.

`AuditService`

- `RecordAuditEvent`: records signed or hashed audit events.

## Language Bindings

Java bindings are generated by Maven for `security-core` from the shared `proto` directory.

The Buf generation config also declares outputs for:

- Java/gRPC under `gateway/target/generated-sources`
- Python under `sdk-python/src`
- JavaScript under `sdk-node/src/generated`

Run generation with:

```powershell
buf generate proto
```

or run the Maven build for Java generation:

```powershell
mvn -pl security-core test
```
